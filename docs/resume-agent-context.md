## 3. Проект: HR Assistant

**Категория:** HR-tech, асинхронные первичные интервью, AI-assisted screening.

**Моя роль:** автор идеи и единственный разработчик; полная реализация и вывод в production.

### Проблема и назначение

Первичный скрининг требует повторяющихся вопросов, согласования времени и ручного разбора ответов. HR Assistant переносит эту часть процесса в асинхронный формат: HR один раз настраивает интервью, кандидат проходит его в Telegram, а HR получает ответы, транскрипции и структурированный AI-разбор в веб-кабинете.

Продукт позволяет проходить первичное интервью без синхронного звонка. Снижение трудозатрат HR — ожидаемая ценность сценария; конкретный размер экономии не измерен в предоставленных материалах.

### Реализованный пользовательский путь

1. HR регистрируется, создаёт вакансию, описание, вопросы и критерии оценки.
2. Для каждого вопроса выбирается текстовый или голосовой ответ; HR может задать скрытые от кандидата ориентиры для AI-разбора.
3. HR передаёт кандидату ссылку на интервью в Telegram.
4. Кандидат последовательно отвечает на вопросы. Система соблюдает дедлайн, формат ответа, ограничения повторной попытки и одного активного интервью.
5. После завершения голосовые ответы расшифровываются в фоне. Ответы с ориентирами HR проходят отдельный AI-разбор.
6. Формируется общий отчёт: резюме, сильные стороны, сомнения, недостающая информация, вопросы для следующего этапа и оценки по заданным критериям.
7. HR изучает отчёт и может перейти от подтверждающей цитаты к исходному ответу. При необходимости доступна пересборка отчёта.
8. Отдельное AI-действие формирует краткую обратную связь кандидату и передаёт её для отправки в Telegram.

AI помогает анализировать ответы и готовить следующий этап. Решение о найме остаётся за человеком.

## 5. Архитектура и инженерные решения

### 5.1. Разделение ответственности между компонентами

Система организована как монорепозиторий. Go-backend содержит HTTP API и обработчики событий интервью. Python-бот отвечает за взаимодействие с Telegram. Отдельный Go-сервис исполняет AI-действия. React-приложение предоставляет кабинет HR. Общий Go-модуль содержит схемы и валидаторы AI-результатов.

```text
HR → React / TypeScript → Go REST API → PostgreSQL

Кандидат → Telegram → Python-бот → RabbitMQ → Go-backend
Кандидат ← Telegram ← Python-бот ← RabbitMQ ← outbox backend

Завершение интервью → AI-задачи через RabbitMQ → Go AI-worker → OpenRouter
Результаты AI → outbox worker → RabbitMQ → backend → отчёт в кабинете HR
Успешный отчёт → задача фидбека → результат → доставка в Telegram
```

В доступном Docker Compose используется общий экземпляр PostgreSQL с отдельной схемой технических таблиц AI-worker. Корректное описание: модульный backend и отдельные сервисы интеграции и обработки. Число процессов само по себе не доказывает независимость микросервисов или масштаб production.

### 5.2. Согласованность при повторной доставке сообщений

Обработка команды кандидата объединяет запись в inbox, изменение интервью и запись исходящего события в одну транзакцию PostgreSQL. ACK брокеру отправляется после фиксации состояния. Повторное сообщение не должно повторять бизнес-изменение; события outbox публикуются с подтверждениями RabbitMQ.

Команды распределяются по восьми очередям на основании Telegram chat ID. Для очередей используются single active consumer и последовательная обработка. Это сохраняет порядок действий в пределах чата. Восемь очередей — параметр реализации, не показатель измеренной производительности.

**Ценность:** обработка повторов и сбоев между БД и брокером без повторного сохранения ответа или продвижения интервью. Общая семантика доставки — at least once; внешний Telegram API допускает дублирование отправки при сбое между отправкой и подтверждением.

### 5.3. Восстановление AI-задач после сбоев

AI-worker содержит четыре типа действий: транскрибация, разбор ответа, общий отчёт и обратная связь. Задания сохраняются в PostgreSQL и забираются исполнителями через `FOR UPDATE SKIP LOCKED` с ограниченным сроком владения — lease.

Задачу с истёкшим lease можно забрать повторно. Временные ошибки повторяются с exponential backoff и jitter; ошибки результата модели имеют отдельный ограниченный бюджет повторов. При завершении результат и событие outbox сохраняются атомарно. Для версионируемых анализов предусмотрена дедупликация и после очистки технических заданий.

**Ценность:** длительные внешние вызовы не блокируют прохождение интервью; предусмотрено восстановление обработки после остановки исполнителя.

### 5.4. Воспроизводимый контекст интервью

При старте интервью фиксируются название и описание вакансии, критерии, вопросы, форматы ответов и ориентиры HR. Редактирование вакансии не изменяет контекст уже начатого интервью. Доменные правила дополнены транзакциями, блокировками и ограничениями БД.

**Ценность:** ответы и результаты AI можно соотнести с теми условиями, которые действовали для конкретной попытки кандидата.

### 5.5. Проверяемые результаты LLM

Текстовые AI-действия используют Structured Outputs и строгие JSON Schema. Приложение проверяет обязательные поля, соответствие критериям и наличие подтверждающих цитат в исходном ответе. Общие валидаторы используются worker и backend.

Недостаток информации представлен как `null`, отдельно от нулевой оценки. Итоговый балл вычисляется приложением по оценённым критериям; вместе с ним показывается покрытие. Без критериев формируется текстовый отчёт без числовых оценок.

Сохраняются версии анализа, промпта и схемы, входной снимок, модель и доступные сведения о расходе токенов. При повторной генерации подсказки об ошибках строятся из допустимых кодов и путей полей, без переноса произвольного текста кандидата в системную инструкцию.

**Ценность:** результаты имеют проверяемую структуру и ссылки на первичный материал. Проверка цитат не гарантирует правильность всех смысловых выводов модели; заявлять устранение галлюцинаций нельзя.

### 5.6. Надёжное поведение интерфейса при фоновой обработке

Пересборка отчёта использует наблюдаемую версию как ключ идемпотентности. Последний успешный отчёт остаётся доступен во время ожидания или ошибки новой версии. Frontend обновляет данные каждые пять секунд, пока отчёт, проверка ответа или транскрипция находятся в ожидании.

В интерфейсе есть переходы из цитат к исходным ответам, возврат к цитате, управление раскрытыми блоками и фокусом. Недостаток данных визуально отличается от низкой оценки.

**Ценность:** HR может продолжать работать с уже готовыми данными и проверять основания AI-выводов.

### 5.7. Управление сессиями и доступом

Пароли хэшируются Argon2id. Refresh credential ротируется; его хэш хранится на сервере. Повторное использование старого refresh отзывает сессию. Активность сессии проверяется для защищённых запросов. HR получает доступ только к принадлежащим ему вакансиям и интервью.

Frontend хранит access token в памяти, использует HttpOnly refresh cookie и объединяет параллельные попытки обновления сессии в один запрос — single-flight. Исходный запрос после `401` повторяется не более одного раза.

**Ценность:** единое управление жизненным циклом сессии и отзывом доступа, согласованное между frontend и backend.

| Сбой AI-worker | Внешний вызов может завершиться ошибкой или исполнитель может остановиться | Durable jobs, lease, повторный захват, backoff, атомарное сохранение результата и события | Предусмотрено восстановление фоновой задачи без повторного интервью |
| Изменение вакансии | HR редактирует вопросы после старта кандидата | Неизменяемый снимок условий интервью | Анализ привязан к контексту конкретной попытки |
| Некорректный AI-результат | JSON может быть невалидным, цитата — отсутствовать в ответе | Строгая схема, семантические проверки, отдельный бюджет корректирующих повторов | Невалидный результат не принимается как успешный |
| Пересборка отчёта | Повторный клик или ошибка новой версии не должны мешать работе HR | Идемпотентность по версии и сохранение последнего успешного результата | Предыдущий отчёт доступен во время повторного анализа |
| Обновление авторизации | Несколько запросов одновременно получают `401` | Single-flight refresh и один повтор исходного запроса | Координация обновления credentials на клиенте |

Эти кейсы описывают реализованные механизмы. Не превращай их в рассказы о конкретных production-инцидентах, если я не сообщал о таких событиях.
