# Проверка ответа по ориентирам HR

Источник требований: `feature-answer-evaluation.md` от 7 сентября 2026 года.

## План реализации

1. Добавить необязательное поле в вопрос, его API и формы; нормализовать пустые значения, фиксировать ориентиры в снимке при старте интервью.
2. Создавать проверку только для завершённого интервью с готовым текстом и ориентирами; использовать транзакционный outbox и существующий registry AI-worker.
3. Вызывать OpenRouter с версионированным промптом и строгой схемой, проверять структуру и дословность цитат перед сохранением.
4. Хранить версии результатов, обрабатывать ошибки и идемпотентный повторный запуск, проверять принадлежность интервью HR.
5. Показывать результат, цитаты, уточняющие вопросы и отдельные состояния обработки; автоматически обновлять карточку.
6. Проверить доменные правила, HTTP API, обработку событий, PostgreSQL, frontend и Docker-сборку.

Все пункты реализованы и проверены. Результаты проверок и порядок запуска приведены ниже.

## Принятые решения

- Поле `evaluationGuide` в HTTP API, `evaluation_guide` в PostgreSQL. Лимит — 4 000 символов; пробельное значение и явный `null` удаляют ориентиры. Старый PATCH без поля сохраняет прежнее значение.
- В интерфейсе одинаковое поле доступно для текстового и голосового вопроса. Описание находится между label и textarea и остаётся видимым.
- Снимок хранит собственные текст вопроса, формат, позицию и ориентиры. Telegram-сообщения содержат только текст и формат вопроса.
- Результат хранится в JSONB с типизированным внешним API. Ключ истории — `(answer_id, version)`. `resultVersion` указывает версию отображаемого успешного результата; `version` — последнюю попытку.
- До 20 пунктов, до 5 цитат на пункт, до 3 уточняющих вопросов. Пустой `checks` допустим, если ориентиры не содержат применимых пунктов; промпт требует пояснение.
- Повторяются до 3 невалидных результатов. Сетевые повторы не расходуют этот бюджет и используют существующий backoff/jitter. Ошибки авторизации и неподдерживаемых параметров завершают попытку с ошибкой, доступной для повторного запуска.
- Повторный запуск доступен для неуспешной проверки. История хранится, отдельного интерфейса истории и ручного перезапуска успешного результата в этой версии нет. Предыдущий успех остаётся видимым при новой обработке или ошибке.
- Нормализация цитат заменяет последовательности Unicode-пробелов одним обычным пробелом и удаляет крайние пробелы. Регистр, слова и пунктуация сохраняются. `found` требует цитату, `not_found` требует пустой массив.
- Общая библиотека `shared/evaluation` содержит схему, типы сообщений и валидатор. Backend повторно проверяет результат перед сохранением; ошибки не содержат входных текстов или ответов провайдера.

## Поток и идемпотентность

Backend сохраняет завершение интервью, pending-транскрипции и существующее событие `interview.completed.v1`. В той же транзакции он создаёт pending-проверки готовых текстовых ответов и события `interview.answer.evaluation_requested.v1`.

Когда backend сохраняет успешную транскрипцию, он тем же способом создаёт запрос проверки голосового ответа. Эта адаптация к текущей архитектуре оставляет выбор снимка и источника текста у владельца данных; worker не читает таблицы интервью. Для отсутствующих ориентиров запрос не создаётся; окончательная ошибка транскрипции возвращается как `skipped` с причиной `transcription_failed`.

Worker принимает запрос через существующую durable очередь и создаёт `answer_evaluation` с уникальностью `(action_type, subject_id, analysis_version)`. Claim, retry и завершение защищены номером попытки и lease. Постоянные компактные записи `completed_evaluations` сохраняют идемпотентность после очистки технических заданий; исходные тексты в них не хранятся.

Успех публикуется как `interview.answer.evaluated.v1`, ошибка — `interview.answer.evaluation_failed.v1`. Backend проверяет answer/session/partition, версии промпта и схемы, валидирует результат и фиксирует его с inbox в одной транзакции. Позднее событие не заменяет уже завершённую версию.

`POST /api/v1/candidates/{sessionId}/answers/{answerId}/evaluation/retry` принимает `{ "version": 1 }`. Номер означает наблюдавшуюся неуспешную попытку. Повторный или одновременный HTTP-запрос создаёт одну следующую версию и возвращает `202 { "version": 2 }`. Чужое интервью возвращает `404`, неподходящее состояние — `409`.

## OpenRouter

Настройка `OPENROUTER_EVALUATION_MODEL` отделена от модели транскрипции; значение по умолчанию — `openai/gpt-4.1-mini`. Ключ и базовый URL используются существующие: `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL`.

Промпт — `openrouter-worker/prompts/answer_evaluation.v1.md`, схема — `shared/evaluation/result.v1.json`. Изменения их смысла требуют новой версии и обработчика соответствующей версии. Передаются `response_format.type=json_schema`, `strict=true`, `provider.require_parameters=true`, в соответствии с [документацией структурированных ответов OpenRouter](https://openrouter.ai/docs/guides/features/structured-outputs). Локальная валидация обязательна независимо от провайдера.

Промпт запрещает выполнять инструкции внутри входных данных, выставлять баллы, принимать решения о найме и оценивать защищённые характеристики. Разбор показывает только сведения из ответа и не утверждает отсутствие навыков на основании отсутствия информации.

## Проверки

- Доменные тесты: пустое поле, редактирование, удаление, Unicode-лимит, сохранение при старом PATCH.
- HTTP-тест с PostgreSQL: создание и чтение ориентиров, `null`, пробелы, pending-результат, авторизация и повторный `202`.
- Интеграционный сценарий: снимок после изменения вакансии, отсутствие ориентиров в Telegram, запуск после завершения, успешная/неуспешная транскрипция, дубликаты событий, ложные цитаты, поздняя ошибка, параллельный retry, предыдущий успешный результат.
- Worker: строгий запрос к локальному HTTP-провайдеру, лимит невалидных результатов, 429/5xx/4xx, безопасные ошибки, версии заданий, lease, повтор после очистки.
- Сквозной тест в отдельных Docker-контейнерах: HTTP → RabbitMQ → worker → локальный HTTP-провайдер → RabbitMQ → backend → успешный результат карточки.
- Визуальная проверка в браузере: поле с сохранёнными ориентирами и видимой подсказкой, готовый разбор и цитаты.
- Frontend: описание поля, оба формата ответа, изменение только ориентиров, очистка в `null`, цитаты и группы разбора, pending/failure, повторный запуск и предыдущий результат.

Команды из соответствующих каталогов:

```bash

# backend и openrouter-worker; отдельная тестовая БД с обеими группами миграций

npm test
npm run build
```

Результат: Go-тесты backend, worker и общей схемы прошли; frontend — 20 тестов, typecheck и production build прошли. ESLint без ошибок, с двумя прежними предупреждениями React Hook Form `watch()`. Docker-образы собираются. Реальные платные AI-запросы при проверках не выполнялись.

## Запуск

Docker-сборка Go-сервисов теперь использует корень проекта как context, чтобы включить `shared`. Корневой `.dockerignore` исключает `.env`, node_modules и артефакты сборки.

Нужны backend-миграция `00013_answer_evaluations.sql` и worker-миграция `00002_answer_evaluations.sql`. При обновлении уже работающего стека сначала остановить старый AI-worker: он использует прежний уникальный ключ заданий. После миграций запустить новую версию backend и worker. `docker compose up --build` остаётся основным способом запуска проекта.


Сквозной тест запускается отдельно, только при поднятом изолированном стеке с
имитацией OpenRouter:

```bash
EVALUATION_QUEUE_E2E=1 E2E_BASE_URL=http://localhost:58086 \
  TEST_RABBITMQ_URL='amqp://...' TEST_DATABASE_URL='postgres://...' \
  go test ./internal/integration -run TestEvaluationThroughRabbitMQ -v
```

Он создаёт тестового HR, вакансию и интервью в одноразовой базе. Их можно
использовать для визуальной проверки до удаления тестового окружения.
