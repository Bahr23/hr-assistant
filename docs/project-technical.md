# HR Assistant — техническое описание

Дата среза: 7 сентября 2026 года.

Документ предназначен для обсуждения архитектуры в другом чате без доступа к репозиторию. Описание основано на исходном коде, OpenAPI, миграциях и Docker Compose. При подготовке документа приложение и тесты не запускались; фактическое состояние развёрнутого окружения не проверялось. Пути ниже указаны относительно корня проекта.

## Назначение и текущий объём

HR Assistant проводит асинхронный первичный скрининг: HR создаёт вакансию и вопросы в веб-кабинете, кандидат проходит интервью в Telegram, завершённые ответы отображаются HR. Голосовые ответы расшифровываются через OpenRouter после завершения интервью.

Реализованы авторизация, управление вакансиями, вопросы, публичные ссылки, состояние кандидатского интервью, просмотр завершённых интервью и транскрибация. Критерии оценки, scoring, summary, отчёты и фидбек пока не реализованы.

## Состав системы

| Часть | Технологии | Ответственность |
|---|---|---|
| `frontend/` | React 19, TypeScript 5.9, Vite 8 | Кабинет HR, формы, вакансии, список и карточка интервью |
| `backend/` | Go 1.25, chi, pgx, sqlc, goose, oapi-codegen | REST API, авторизация, доменные правила, состояние интервью, RabbitMQ consumers и outbox |
| `telegram-bot/` | Python 3.13, aiogram 3, aiohttp, aio-pika, pydantic-settings | Получение Telegram updates через polling, публикация команд, оформление и доставка сообщений |
| `openrouter-worker/` | Go 1.25, pgx, goose, RabbitMQ client | Долговечные задания транскрибации, скачивание аудио, OpenRouter API, события результата |
| `cleanup-worker` | Отдельный исполняемый файл из `backend/` | Периодическая очистка технических таблиц backend |
| PostgreSQL | Образ PostgreSQL 17 в `.env.example` | Основное состояние и очереди фоновых заданий в таблицах |
| RabbitMQ | Образ RabbitMQ 4.1.8 Management в `.env.example` | Передача команд и событий между процессами |

Версии отражают манифесты и пример конфигурации проекта. Backend и AI-worker — отдельные Go-модули. Сервисы запускаются через корневой `compose.yml`; он также содержит одноразовые задачи миграций обеих частей и создания AI-очередей.

Backend совмещает HTTP API и обработку событий интервью в одном процессе. AI-обработка и Telegram-адаптер вынесены в отдельные процессы. В локальном Compose используется один PostgreSQL: бизнес-таблицы backend и отдельная схема `openrouter_worker` для технического состояния AI.

## Поток данных

```text
HR → React → REST API → PostgreSQL

Кандидат → Telegram → Python-бот
                         │
                         ├─ REST: получить приветствие и проверить попытку
                         │
                         └─ RabbitMQ: candidate.commands
                                      ↓
                               Go backend
                                      │
                         транзакция: inbox + интервью + outbox
                                      │
                         RabbitMQ: telegram.commands
                                      ↓
                               Python-бот → Telegram

Завершение интервью → interview.events → OpenRouter worker
                                             │
                            PostgreSQL job → Telegram getFile
                                             ↓
                                     OpenRouter API
                                             │
                            результат + outbox → interview.events
                                             ↓
                              backend → транскрипция в PostgreSQL
                                             ↓
                                      REST API → HR
```

RabbitMQ передаёт команды; подтверждённое состояние интервью хранится в PostgreSQL. Отправка сообщения кандидату о завершении не ждёт AI. Веб-карточка получает расшифровки следующим запросом, включая ручное обновление; отдельного механизма push-обновлений нет.

## Backend и границы модулей

`backend/cmd/api/main.go` собирает зависимости, запускает HTTP-сервер и обработчики RabbitMQ, управляет остановкой. В `internal/app/` находятся:

- `auth/{transport,service,repository}` — регистрация, вход, проверка и отзыв сессий.
- `vacancy/{transport,service,repository}` — вакансия, вопросы и публичная ссылка как один транзакционный агрегат.
- `candidate/{transport,service,repository}` — чтение завершённых интервью для HR с проверкой владельца вакансии.
- `interview/worker` — обработка команд кандидата, переходы состояния, дедлайны, доставки и результаты AI.
- `cleanup/worker` — очистка технических записей.

`internal/core/` содержит доменные сущности, конфигурацию, подключение к БД, generated sqlc-код, RabbitMQ topology, логирование и общий HTTP router. Доменные правила не зависят от HTTP; преобразование HTTP DTO и моделей хранения выполняют адаптеры. Для основных CRUD-запросов используется sqlc, в обработке интервью и чтении кандидатов есть SQL непосредственно через pgx.

## Основные данные и инварианты

| Сущность / таблицы | Содержание и правила |
|---|---|
| `users`, `sessions` | HR и серверные сессии с хэшем refresh credential |
| `vacancies`, `questions` | Владелец, название, язык, приветствие, общий лимит времени, необязательный срок приёма новых интервью, статус, токен ссылки и упорядоченные вопросы |
| `telegram_candidates` | Telegram user/chat ID, имя, фамилия, username, язык, Premium и даты первого/последнего контакта |
| `interview_sessions` | Попытка на вакансию, текущий вопрос, дедлайн, статусы `active`, `completed`, `cancelled`, `expired` |
| `interview_attempt_claims` | Уникальная пара «вакансия + Telegram-пользователь», запрещающая повторную попытку |
| `interview_session_questions` | Копия текста, формата и порядка вопросов на момент старта |
| `interview_answers` | Один ответ на позицию вопроса: текст либо Telegram `file_id` и метаданные голосового сообщения |
| `interview_answer_transcriptions` | Постоянная расшифровка, статус, модель, ошибка и технические сведения о попытках и usage |
| `telegram_deliveries`, `inbox_messages`, `outbox_events` | Состояние доставки, дедупликация входящих сообщений и события для публикации |

В схеме `openrouter_worker` находятся `inbox_events`, `action_jobs`, `voice_transcription_jobs` и `outbox_events`. Уникальность `(action_type, subject_id)` исключает повторное создание задания одного типа для того же ответа.

Ключевые правила реализации:

- HR получает доступ только к своим вакансиям и их завершённым интервью; недоступная чужая запись возвращается как не найденная.
- Вакансия создаётся сразу в `published`; второе допустимое состояние — `archived`. Активная конфигурация требует заполненных обязательных полей и хотя бы одного вопроса. Черновиков в текущем контракте нет.
- Изменения вакансии, вопросов и ссылки сериализуются блокировкой вакансии. Порядок вопросов плотный, начиная с нуля; перестановка должна содержать каждый существующий вопрос ровно один раз.
- Архивирование удаляет публичный токен, восстановление и перевыпуск дают новый. Уже начатые сессии продолжаются в пределах собственного дедлайна.
- У кандидата только одна активная сессия, что дополнительно закреплено частичным уникальным индексом. Попытка на ту же вакансию не возобновляется после отмены или истечения срока.
- При старте фиксируются вопросы и дедлайн: начало плюс 5, 15, 30 или 60 минут. Изменение вопросов вакансии не меняет уже созданную копию.
- Текст принимается только на текстовый вопрос, Telegram voice — только на голосовой. Ответ сохраняется сразу и продвигает сессию; отдельного шага подтверждения нет.
- API `/candidates` возвращает завершённые сессии, а идентификатор карточки кандидата — `sessionId`, не глобальный ID профиля.

## HTTP-контракт и frontend

Базовый путь API — `/api/v1`. Источник контракта — `backend/openapi/openapi.yaml`.

| Группа | Основные операции |
|---|---|
| `/auth` | `register`, `login`, `refresh`, `logout`, `me` |
| `/vacancies` | Создание, список, чтение, обновление, archive/restore, перевыпуск ссылки |
| `/vacancies/{vacancyId}/questions` | Создание, изменение, удаление и перестановка вопросов |
| `/vacancies/public/{publicToken}` | Приветствие и проверка предыдущей попытки; служебный доступ бота через master token или доступ с bearer credential |
| `/candidates` | Поиск завершённых интервью по имени/username, фильтр `vacancy_id`, пагинация `limit`/`offset` |
| `/candidates/{sessionId}` | Завершённое интервью с вопросами, ответами и состояниями транскрибации |

Несмотря на слово `public` в пути, endpoint приветствия требует авторизацию. Публичная ссылка для кандидата ведёт в Telegram. Ответы кандидата поступают через RabbitMQ, отдельного публичного REST API прохождения нет.

OpenAPI генерирует три локальных Go-контракта: auth, vacancy и candidate. TypeScript-типы генерируются из того же файла в `frontend/src/shared/api/schema.generated.ts`; клиент использует `openapi-fetch`.

Frontend разделён на `app`, `pages`, `widgets`, `features`, `entities`, `shared`. Server state хранится в TanStack Query; формы используют React Hook Form, стили — CSS Modules и общие tokens. Визуальные правила описаны в `frontend/DESIGN.md`. Есть страницы входа, регистрации, списка/создания/редактирования вакансий, списка/карточки кандидатов и настроек аккаунта.

Интерфейс показывает текстовые ответы и транскрипции со статусами `pending`, `succeeded`, `permanent_failed`. Аудиоплеера нет. Web-формы фиксируют язык `ru`; API позволяет задавать язык, срок приёма новых интервью и перевыпускать ссылку, но эти настройки представлены в UI не полностью.

## Авторизация

Пароли хэшируются Argon2id, email нормализуется. Access JWT передаётся в `Authorization: Bearer`, по умолчанию живёт 15 минут и хранится frontend только в памяти. Refresh JWT находится в `HttpOnly`, `SameSite=Lax` cookie и по умолчанию живёт 30 дней; в production включается `Secure`.

В БД хранится SHA-256 хэш текущего refresh credential. Обновление ротирует его; повторное использование старого отзывает сессию. Каждый защищённый запрос проверяет активность сессии в БД, поэтому logout отзывает и ранее выданные access credentials. На frontend обновление токенов выполняется single-flight, после `401` исходный запрос повторяется максимум один раз.

Login и register ограничены десятью запросами с одного IP в минуту на экземпляр backend. CORS настроен на `FRONTEND_ORIGIN`. Бот использует отдельный `MASTER_API_TOKEN`; секреты задаются через окружение, реальные значения из `.env` в этот документ не включены.

## Очереди и обработка сбоев

Для команд кандидата и исходящих Telegram-сообщений используются восемь фиксированных shard-очередей: `telegram_chat_id % 8`. Основные exchanges — `candidate.commands`, `telegram.commands`, `interview.events`; ошибочные сообщения направляются через `dead.letters`.

Основные очереди — durable quorum queues с single active consumer и `prefetch=1`. Команды одного чата попадают в одну очередь и обрабатываются последовательно. Число shards — часть текущего протокола; его нельзя просто изменить в настройке без миграции очередей и маршрутизации.

Обработка команды backend выполняется одной транзакцией: запись `message_id` в inbox → блокировка и изменение сессии → запись ответа и исходящего события → commit → ACK брокеру. Повтор уже обработанного сообщения не повторяет бизнес-изменения. Outbox публикуется с publisher confirms; advisory lock выбирает одного активного publisher среди реплик.

Общая гарантия доставки — at least once. Сбой после внешней отправки, но до записи подтверждения допускает повтор; например, кандидат может получить дубликат Telegram-сообщения. Inbox/outbox не обеспечивают exactly once для внешнего Telegram API.

Telegram sender по умолчанию ограничивает отправку двумя сообщениями в секунду на shard и одним на чат. Обрабатываются `429` и временные ошибки. Это настройки реализации, не подтверждённый нагрузочным тестом предел системы.

## Транскрибация

1. При завершении интервью backend создаёт `pending`-записи для голосовых ответов и событие `interview.completed.v1`.
2. AI-worker сохраняет событие и отдельное задание на каждый голосовой ответ в PostgreSQL; после commit подтверждает сообщение RabbitMQ.
3. Исполнители забирают задания через `FOR UPDATE SKIP LOCKED` с lease. По умолчанию их четыре; lease — 10 минут.
4. Для каждой попытки worker вызывает Telegram `getFile` и скачивает аудио во временный каталог. Лимит реализации — 20 МБ. В Compose каталог размещён в `tmpfs`; временные файлы удаляются после попытки.
5. Аудио отправляется как base64 в OpenRouter `/audio/transcriptions`. Модель по умолчанию в конфигурации — `openai/gpt-4o-mini-transcribe`, HTTP timeout — 5 минут. Это настроенное значение; доступность модели и внешнего API здесь не проверялась.
6. Результат и событие записываются одной транзакцией. `interview.voice.transcribed.v1` или `interview.voice.transcription_failed.v1` возвращается backend через `interview.events`.
7. Backend идемпотентно обновляет постоянную транскрипцию, которую затем читает HR API.

Временные ошибки повторяются без ограничения числа попыток, с exponential backoff и jitter, до 30 минут между попытками. Невалидный файл, превышение размера и неподдерживаемое аудио могут завершиться `permanent_failed`. Длительный сбой внешнего сервиса может оставлять интерфейс в `pending`.

Registry AI-worker сейчас содержит только `voice_transcription`. Добавление summary/scoring потребует новых обработчиков, схем данных, событий и представления результата в кабинете.

## Хранение, запуск и проверки

Backend cleanup по умолчанию удаляет inbox старше 30 дней, опубликованный outbox старше 7 дней и завершённые доставки старше 90 дней. Непубликованные события и `pending`-доставки остаются. Очистка выполняется раз в час порциями по 1000 записей.

AI-worker отдельно очищает inbox через 30 дней, опубликованный outbox через 7 дней и завершённые jobs через 90 дней. Кандидаты, интервью, ответы и постоянные транскрипции автоматически не удаляются. Долговременного собственного хранилища аудио нет: в backend сохраняется Telegram `file_id` и метаданные.

Для первого локального запуска из корня проекта:

```bash
cp -n .env.example .env
# Заполнить .env перед запуском.
docker compose up --build
```

Нужны Docker Compose и доступы к Telegram/OpenRouter. В `.env` задаются `BOT_TOKEN`, `TELEGRAM_BOT_URL`, `OPENROUTER_API_KEY`, `JWT_SECRET`, `MASTER_API_TOKEN` и подключения к БД/брокеру. JWT и master secret должны быть не короче 32 символов; master secret должен совпадать у backend и бота. Пример конфигурации содержит локальные значения и заглушки, которые нужно заменить. Если `.env` уже есть, используются его настройки.

При значениях из `.env.example`: frontend — `http://localhost:5173`, API — `http://localhost:8080`, PostgreSQL для клиента на хосте — `localhost:5450`, RabbitMQ Management — `http://localhost:15672`. Контейнеры подключаются к PostgreSQL через `DATABASE_URL`, клиент на хосте — через `DATABASE_EXTERNAL_URL`.

Проверка готовности:

```bash
curl http://localhost:8080/health/ready
docker compose exec openrouter-worker /app/openrouter-worker healthcheck
```

Backend предоставляет `/health/live` и `/health/ready`; его readiness проверяет PostgreSQL и сам по себе не подтверждает работу Telegram, RabbitMQ и OpenRouter. Есть JSON-логи Go-сервисов, но отдельного стека метрик и алертов в Compose нет.

Команды разработки, каждая из указанного каталога:

| Каталог | Команды |
|---|---|
| `backend/` | `make generate` — sqlc и все Go OpenAPI-контракты; `make test` — Go-тесты |
| `openrouter-worker/` | `go test ./...` |
| `telegram-bot/` | `python -m pip install -r requirements.txt`, затем `python -m unittest discover -s tests` |
| `frontend/` | `npm install`, `npm run generate:api`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build` |

В коде есть unit-тесты, проверки HTTP-контрактов, repository/integration-тесты, HTTP E2E и frontend-тесты на Vitest/Testing Library. Интеграционные Go-тесты требуют `TEST_DATABASE_URL` и применённых миграций; HTTP E2E — `E2E_BASE_URL` запущенного backend. Без соответствующих переменных эти проверки пропускаются. Для интеграционных тестов нужна отдельная тестовая БД, поскольку они изменяют данные. Наличие тестов здесь не означает, что они были выполнены при подготовке документа.

## Что важно для следующих технических решений

- **Продуктовая модель.** Нынешний read API показывает только завершённые интервью. Воронка, рабочие пространства, роли и HR-заметки потребуют расширить модель и права доступа.
- **Новые AI-функции.** Нужно определить критерии, версионирование анализа, формат результата и способ проверки HR до реализации scoring/summary.
- **Исходные записи.** Для прослушивания и независимого хранения потребуется решить вопросы получения аудио, контроля доступа и срока хранения.
- **Эксплуатация.** Compose ориентирован на локальную разработку: frontend запускается в Vite dev server с HMR. Production-развёртывание, резервное копирование и мониторинг не описаны здесь как готовая инфраструктура.
- **Масштабирование.** Backend HTTP и интервью-workers имеют общий процесс; shards фиксированы, outbox имеет одного активного publisher, Telegram-бот использует polling. Эти ограничения нужно учитывать перед увеличением количества реплик.
- **Наблюдаемость и восстановление.** Для эксплуатации полезно определить контроль зависших AI-заданий, старых `pending`-транскрипций, DLQ и безопасного replay. Inbox дедупликация ограничена сроком хранения технических записей.
